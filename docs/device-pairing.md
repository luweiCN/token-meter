# 设备配对协议

桌面、CLI 与手机使用同一套邀请、身份和权限。每个安装实例持有自己的 Ed25519 长期密钥。普通操作见[设备与命令行](device-sync.md#连接两台设备)。

## 邀请和连接

邀请设备生成一次性的 Ed25519 中继监听身份、房间号和两份独立口令。房间号和手输口令各为 6 个均匀随机字符，字符集为 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`。手输格式是两者拼接后每四位加一个连字符。客户端接受大小写、半角空格和连字符。

邀请链接及二维码为 `tokenmeter://pair/ROOM#v1.SECRET`。SECRET 是 24 个随机字节的无填充 base64url 编码。链接里的口令保留在 fragment。两种凭据使用相同的认证协议。客户端只向中继发送小写房间号，解析出的目标是邀请过程的临时监听身份。中继地址来自本地配置。邀请最长有效十分钟，经过三次认证失败即关闭，获准的邀请只能使用一次。关闭创建邀请的界面会撤销会合。

两边各自向 HTTPS 服务建立出站 WebSocket。中继传输握手、挑战签名和会合帧由[中继协议](../internal/relay/protocol.go)定义。取得双向字节流后，发起方担任内层 TLS 服务端，加入方为客户端。双方使用 TLS 1.3，ALPN 为 `tokenmeter-pair/1`，提供长期 Ed25519 自签名证书并证明持有私钥，不使用 TLS 会话票据。设备 ID 是单张对端证书中的 Ed25519 公钥的小写十六进制编码。首次配对通过下文的口令证明验证证书对应的双方身份，再交换设备名称、直连地址和授权。

## 口令认证

TLS 中的每个帧由一个大端 uint16 长度和对应长度的 UTF-8 JSON 对象组成，最大 4096 字节。二进制 `data` 字段使用标准有填充 base64。

1. 加入方发送 `{"type":"join","mode":"manual","role":"peer"}`。扫码或粘贴链接时 mode 为 `link`。发起方发送 `{"type":"offer","role":"peer"}`。任一方请求 `viewer` 时，实际角色为 `viewer`。
2. 导出 32 字节 TLS keying material，标签为 `EXPORTER-TokenMeter-pair-v1`，context 是空字节串。OPAQUE context 为 UTF-8 字符串 `tokenmeter-pair/1`、小写房间号和实际角色分别接一个零字节，再接这 32 字节。OPAQUE 使用 Ristretto255/SHA-512 及 Argon2id。Argon2id 的盐为该 context 的 SHA-256 前 16 字节，时间参数 3，内存 65,536 KiB，并行度 4，输出 32 字节。客户端身份为加入方设备 ID 的 ASCII 字节，服务器身份为发起方设备 ID 的 ASCII 字节。
3. 发起方在设备内用对应口令生成临时 OPAQUE 注册记录。手输口令为大写的 6 个字符，链接口令是 fragment 中 `v1.` 后的 32 个字符，两者均用原始 ASCII 字节。每次认证使用独立的服务器密钥、OPRF 种子和 credential identifier，注册消息留在本机。加入方和发起方依次交换 `ke1`、`ke2`、`ke3` 帧，`data` 为 RFC 序列化的 OPAQUE 消息。加入方验证服务器，发起方验证 KE3 后才可使用 session secret。[RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html)
4. 发起方先、加入方后发送 `{"type":"device","device":{"id":"…","name":"…","address":"…"}}`。ID 必须与刚验证的对端证书公钥一致。名称使用 UTF-8 且至多 255 字节，地址可省略，提供时为私网 IP 字面量与端口。两端分别计算校验码并向用户显示对端名称与权限。

校验码使用 OPAQUE session secret 作为 HMAC-SHA-256 密钥。依次编码协议名、角色、发起方 ID、发起方名称、发起方地址、加入方 ID、加入方名称、加入方地址。每项都是 2 字节大端长度和对应的 UTF-8 字节。地址省略时编码空串。将 HMAC 输出的前 4 字节视为大端无符号整数，模 1,000,000，补足六位，按三个数字一组显示。跨语言测试向量见 [TestPairVerificationInteroperability](../internal/device/pair_test.go)。

## 确认与权限

两端都展示同一校验码。双向同步要求两位设备所有者各自确认。只读邀请由共享数据的一方确认。加入端有权请求降低至只读。等待过程中，端点可每 25 秒发送一个 `keepalive` 帧。

每方同意后发送 `consent`。拒绝发送 `rejected` 并终止。双方同意后，各端在本机事务中暂存对端身份、权限、名称、可用的直连地址和中继地址。加入方发 `ready` 表明本机已准备保存；发起方提交并发 `saved`；加入方提交并回 `saved`。准备失败的一方关闭流，对方回滚未提交事务。如果最终回执传输中断，已提交的一方会告知用户可按相同权限重新配对核对。改变已保存的权限需要先解除原配对。

| 发起方选择 | 发起方记录 | 加入方记录 |
| --- | --- | --- |
| 双方均同意双向同步 | `peer` | `peer` |
| 只读查看 | `viewer`（允许对端查询） | `source`（仅主动向对端查询） |

后续连接使用已固定的长期设备公钥，优先尝试私网直连，再尝试双方已接受的 HTTPS 中继。用量、额度和同步数据由原有内层双向 TLS 保护。服务端对每个请求检查设备身份和权限。每份只读授权由提供数据的设备独立作出。
